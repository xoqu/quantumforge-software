# Задание 1. Исследование моделей и инфраструктуры

## 1. Резюме решения

Для QuantumForge Software рекомендуется **гибридная архитектура**:

- **ChromaDB в серверном режиме** как векторная база;
- локальная модель эмбеддингов **BAAI/bge-m3** из экосистемы Sentence-Transformers;
- **GPT-5 mini через API OpenAI** для документов класса Public/Internal;
- локальная **Qwen3-14B-AWQ** для Confidential/Restricted и как резервный контур;
- раздельные коллекции ChromaDB по областям доступа с обязательной фильтрацией по ACL до передачи контекста в LLM.

Такой вариант обеспечивает высокое качество ответов на основном потоке, не передаёт наиболее чувствительные фрагменты внешнему провайдеру и не требует держать дорогую GPU-инфраструктуру под всей нагрузкой.

Выбранная векторная БД — **ChromaDB**, потому что при ожидаемом объёме она даёт достаточно высокую скорость, хранение метаданных и фильтрацию прав доступа, персистентность и клиент-серверный режим. FAISS быстрее и гибче как низкоуровневая библиотека, но функции БД — API, метаданные, конкурентный доступ, резервное копирование и эксплуатационные процедуры — пришлось бы создавать самостоятельно.

## 2. Заказчики и пользователи

Инициатор решения — техническое руководство (CTO/CIO) совместно с владельцем корпоративной базы знаний. Решение также должны согласовать Information Security, Legal/DPO и GRC, потому что бот будет обрабатывать внутренние документы и материалы аудита.

Пользователи и их приоритеты:

- разработчики — точные ответы по API, ADR и микросервисам со ссылками на источник;
- поддержка — быстрый поиск проверенных инструкций;
- менеджеры и аналитики — актуальные регламенты и бизнес-правила;
- новые сотрудники — понятные onboarding-инструкции;

Главные критерии: корректность найденных источников, отсутствие утечки данных, цитирование, актуальность, задержка и стоимость владения.

## 3. Исходные данные и допущения

Исходный корпус содержит около 21 250 документов: 18 000 Markdown/MDX-файлов, 3 000 страниц Confluence и 250 PDF. Прирост — около 400 страниц в месяц.

Для предварительной оценки приняты следующие допущения:

- после очистки и OCR — около 50 млн токенов;
- разбиение по 500–800 токенов с перекрытием даст ориентировочно 100–300 тыс. чанков;
- рабочая нагрузка — 30 000 вопросов в месяц;
- один запрос к LLM — в среднем 3 000 входных и 500 выходных токенов;
- расчёты не включают зарплату команды, налоги, сетевой трафик и enterprise-скидки;
- цены API меняются, поэтому перед закупкой их нужно повторно проверить в калькуляторах провайдеров.

Для 300 тыс. векторов BGE-M3 размерностью 1024 необработанные векторы float32 займут примерно 1,23 ГБ. Индекс HNSW, документы и метаданные увеличат объём в несколько раз, но весь рабочий набор всё равно помещается в 32–64 ГБ RAM.

## 4. Сравнение LLM

Для сравнения выбрана **Qwen3-14B-AWQ**: модель поддерживает более 100 языков, имеет нативный контекст 32 768 токенов, лицензию Apache 2.0 и 4-битную квантизацию. В качестве облачных представителей выбраны **GPT-5 mini** и **YandexGPT Pro 5.1**.

| Критерий | Qwen3-14B-AWQ локально | OpenAI GPT-5 mini | YandexGPT Pro 5.1 |
| --- | --- | --- | --- |
| Качество | Достаточное для типового RAG, суммаризации и закрытого контура. Обычно уступает сильной облачной модели в сложном рассуждении и соблюдении длинных инструкций | Высокое качество сложных и многоязычных ответов, большой контекст, однако качество может меняться при смене версии или обновлении модели провайдером | Сильная работа с русским языком. Качество на английском, финском, эстонском и программном коде нужно проверять на корпусе компании |
| Скорость | Предсказуема и не зависит от внешней сети. На одной GPU 24 ГБ пригодна для небольшой параллельной нагрузки; скорость заметно падает с ростом контекста и числа одновременных запросов | Нет развёртывания модели; хорошее масштабирование API. Задержка зависит от сети, квот и провайдера | Аналогично OpenAI: быстрый старт, но есть сеть, квоты и зависимость от доступности сервиса |
| Стоимость | Нет оплаты за токены, но GPU оплачивается даже при простое, если узел работает постоянно. Дополнительные расходы: MLOps, мониторинг, обновления, резервирование | На дату анализа GPT-5 mini: $0,25 за 1 млн входных и $2 за 1 млн выходных токенов. При принятых допущениях — около $52,50 в месяц без кеширования | Оплата за токены. Ориентир для Pro 5.1 из доступных публикаций — 0,8 ₽ за 1 000 входных и выходных токенов, то есть около 84 000 ₽ в месяц по принятому сценарию |
| Развёртывание | Самое сложное: vLLM/TGI, драйверы CUDA, квантизация, autoscaling, наблюдаемость, обновления и контроль лицензий | Самое простое: API, SDK, управление ключами, лимитами и бюджетом | Аналогично OpenAI |
| Конфиденциальность | Данные остаются в VPC компании | Данные покидают контур. OpenAI не использует API-данные для обучения по умолчанию, но abuse-monitoring logs обычно хранятся до 30 дней | Данные обрабатываются в инфраструктуре Yandex Cloud. Для финско-эстонской компании необходимы отдельная GDPR/DPA, санкционная и трансграничная правовая оценки |
| Vendor lock-in | Низкий: модель и runtime можно заменить | Средний/высокий: API, тарифы, квоты и жизненный цикл модели контролирует провайдер | Аналогично OpenAI |

Расчёт OpenAI для 30 тыс. запросов: 90 млн входных токенов × $0,25/млн + 15 млн выходных × $2/млн = **$52,50/месяц**. Это только генерация. Фактический счёт зависит от длины найденного контекста, reasoning tokens и кеширования.

**Вывод по LLM:** для PoC и основного неконфиденциального трафика лучше OpenAI: качество и скорость запуска важнее небольшой оплаты за токены. Для секретов, исходного кода с ограниченным доступом, клиентских PDF и доказательств SOC 2 нужен локальный маршрут. YandexGPT не выбран основным: его преимущество в русском языке менее важно для финско-эстонской компании, а новый регион обработки данных и отдельный провайдер увеличивают юридические и операционные риски.

## 5. Сравнение моделей эмбеддингов

Рассматриваются локальная **BAAI/bge-m3** через Sentence-Transformers/FlagEmbedding и облачные **OpenAI text-embedding-3-small/large**.

| Критерий | BGE-M3 локально | OpenAI Embeddings |
| --- | --- | --- |
| Создание индекса | На GPU данные обрабатываются локально пакетами без сетевых задержек и внешних квот. На CPU первичная индексация будет заметно дольше, но инкремент в 400 страниц/месяц невелик | Не нужно выделять GPU; батчи легко отправлять параллельно. Скорость зависит от сети и лимитов |
| Качество поиска | Более 100 языков, вход до 8 192 токенов, вектор 1024. Поддерживает dense, sparse и multi-vector режимы; для ChromaDB в первой версии используется dense. Хорошо подходит многоязычному корпусу | `text-embedding-3-small`: 62,3% MTEB, `large`: 64,6% по данным OpenAI; обе модели принимают до 8 192 токенов. Результат нельзя напрямую сравнить с BGE-M3 без одинакового набора запросов |
| Стоимость | Модель бесплатна по API, но нужны CPU/GPU, электроэнергия/облако и сопровождение. | `small` — $0,02, `large` — $0,13 за 1 млн входных токенов. Индексация 50 млн токенов стоит примерно $1 или $6,50 соответственно |
| Конфиденциальность | Исходный текст не выходит из контура | Для построения эмбеддинга текст отправляется в OpenAI |
| Переносимость | Полный контроль версии; можно повторно получить тот же индекс | Смена модели или размерности требует полной переиндексации; жизненный цикл контролирует провайдер |

Дешевизна OpenAI Embeddings сама по себе не делает этот вариант лучшим: при построении индекса провайдеру необходимо передать **весь исходный корпус**. Локальная BGE-M3 устраняет эту проблему, а GPU требуется преимущественно при первичной и пакетной индексации.

## 6. Сравнение ChromaDB и FAISS

| Критерий | ChromaDB | FAISS |
| --- | --- | --- |
| Назначение | Векторная БД: коллекции, документы, метаданные, фильтры, персистентность, HTTP-клиенты | Библиотека алгоритмов nearest-neighbor search; не самостоятельная БД |
| Поиск | HNSW обеспечивает быстрый аппроксимированный поиск. Для объёма в сотни тысяч чанков задержка будет достаточной без GPU | Очень быстрый поиск; широкий выбор Flat, IVF, PQ и GPU-индексов. Даёт больше возможностей точной настройки speed/recall/memory |
| Индексация | Проще: добавление документов и метаданных через API. Дополнительные full-text и metadata-индексы повышают стоимость записи | Flat-индекс не требует обучения; IVF/PQ требуют обучения и ручного подбора параметров |
| Внедрение | Низкий порог входа, Python/JS-клиенты, Docker, серверный режим | Легко начать в одном Python-процессе, но multi-user API, хранение документов, ACL-фильтры, обновления, блокировки и backup нужно реализовать отдельно |
| Поддержка | Single-node подходит текущему объёму; при росте есть распределённая архитектура. Индекс должен помещаться в RAM, иначе swap резко ухудшит задержку | Сам индекс экономичен, но эксплуатационный код становится ответственностью команды. GPU-индекс перед сохранением нужно переносить на CPU |
| Стоимость | Open-source ПО бесплатно; расходы на RAM, SSD, backup и эксплуатацию сервера | Библиотека бесплатна и может иметь меньший инфраструктурный overhead, но скрытая стоимость собственной обвязки выше |
| Удобство для RAG | Выше: текст, вектор и metadata находятся в одной коллекции; удобно фильтровать по `source`, `version`, `team`, `classification`, `acl_groups` | Ниже: FAISS возвращает идентификаторы и расстояния; отдельное хранилище должно разрешить ID в текст и проверить права |

По документации Chroma `PersistentClient` предназначен для локальной разработки и тестирования. В production следует использовать **server-backed Chroma с async HTTP client**, отдельным диском и резервным копированием. Для текущих 100–300 тыс. чанков распределённый режим избыточен.

**Вывод по векторной БД:** выбрать **ChromaDB single-node в серверном режиме**. FAISS разумен для лабораторного benchmark или встраиваемого однопроцессного прототипа, но не как корпоративная многопользовательская база без дополнительного сервисного слоя.

## 8. Рекомендуемая конфигурация сервера

### Production

Лучше разделить разные профили нагрузки:

1. **RAG API + ChromaDB:** 16 vCPU, 64 ГБ RAM, 1 ТБ SSD/NVMe, не менее 3 000 IOPS, без GPU. Chroma разворачивается в AWS рядом с существующим EKS; данные и snapshots шифруются, backup копируется в S3.
2. **Локальный inference/индексация:** 16–24 vCPU, 64–128 ГБ RAM, NVIDIA L4 24 ГБ как минимум. Для большего контекста и параллельности — L40S 48 ГБ. Узел запускается по требованию или масштабируется до нуля, если политика и платформа это допускают.

Минимальная конфигурация для пилота: **16 vCPU, 64 ГБ RAM, NVIDIA L4 24 ГБ, 1 ТБ NVMe**. Она достаточна для Qwen3-14B-AWQ, BGE-M3 и текущего индекса, но не обеспечивает высокой доступности.

Для production необходимо минимум два экземпляра stateless RAG API. Single-node Chroma следует защитить health checks, persistent volume, snapshots и проверенным восстановлением. Переход к distributed Chroma нужен не из-за текущего числа документов, а при необходимости высокой доступности, десятков миллионов векторов или устойчиво высокой параллельной записи.

## Словарь замен

Для замен использовался генератор случайных имен.

Словарь сохранён в `terms_map.json`.

В словарь включены полные имена, короткие формы, фамилии, псевдонимы, корпорации, банды, локации, технологии, события и характерные годы. Для нескольких русских терминов добавлены падежные формы, чтобы итоговый текст оставался грамматически связным.

## Логика замен

1. Для замен использовалась нейросеть.
2. Ключи сортировались по убыванию длины: сначала `Night City Police Department`, затем `Night City`, но не наоборот.
3. Выполнялся один regex-проход по исходному тексту, чтобы новые значения повторно не заменялись другими правилами.
4. Для коротких ключей применялись границы слова `V`, `BD` и `Alt`.

```bash
  -H "Content-Type: application/json" \
  -d '{
    "question": "Задайте вопрос по загруженным документам",
    "protection": "all"
  }'
```

## Использованная защита

- Защитный system prompt запрещает выполнять команды из документов.
- Управляющие конструкции вроде `Ignore all instructions` удаляются.
- Ответ проверяется на утечку тестового секрета.
- При отсутствии безопасного контекста бот отвечает: «Я не знаю».

Корректное поведение наблюдается в режиме `all`: вредоносный чанк блокируется, секрет не попадает в ответ, а отсутствующая информация не выдумывается.

Потенциально уязвим режим `none`, где документ передаётся модели без защиты. Один system prompt также недостаточен. Regex-фильтры могут обходиться перефразированием или кодированием, поэтому в production дополнительно нужны классификатор prompt injection, ACL и аудит.
